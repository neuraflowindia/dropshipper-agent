## 3. Yield must be in every recurring forecast

The preserved legacy baseline has156 working concepts,11 ready products,107 set aside and38 unfinished: **7.05% readiness under the historical seven-of-thirteen policy**. Current local code uses ten criteria with Good>=6/Decent=5; its actual saved-data/sample counts live in the benchmark. Reinterpreting existing inventory is not new collection yield and does not justify retroactively reducing the original expense. The old five-/six-score bins cannot be relabelled current readiness, and unfinished products are not rejected.

Use three separately labelled calculations:

1. Collection yield measures distinct useful concepts from the actual returned records.
2. Completed-screening yield measures eligible products among products whose required screening was actually finished.
3. New-product supply measures eligible, never-published-to-this-client products after identity, freshness and queued reservations. Carryover can fill a report, but depletes an existing pool rather than increasing fresh discovery yield.

For a rough sensitivity calculation only:

- Collection expense per working idea = US$0.50040006 / 156 = approximately US$0.00320769.
- Required ideas = ceiling(required new recommendations / assumed readiness).
- Forecast collection expense = required ideas × that observed expense per idea.

## 4. Calendar, pooled research and account periods

Count the actual Tuesday/Thursday/Saturday release dates: usually 12–14 monthly, not always four weeks × three. Minimum entry totals are 120/130/140. At the 80% rule, minimum New totals are 96/104/112 **only if useful updates exist**; forecasts above deliberately assume none.

Do not multiply a weekly collection cost three times merely because it produces three issue files. Conversely, do not divide cost by three unless the same batch actually yields enough distinct eligible inventory for all three. Preparing 35 eligible products once can supply three ten-item minimums plus five extras; eleven ready products cannot be portrayed as a ready three-issue week.

Separate:

- Provider allowance period and account: owns collection/read charges and unknown commitments.
- Research batch date: owns work actually executed.
- Issue release date: owns client availability, not when research was collected.
- Shared acquisition: charged once even if it supports multiple candidates or issues.
- Issue-specific validation, supplier work and writing: attributed directly where possible.

Keep one acquisition cost total, then use an explicit allocation rule for shared weekly expense—for example, divide by actual frozen product allocations when their benefit cannot be separated. Save the rule and unallocated backlog/development share. Both language editions of one issue are one research issue, not two acquisition charges.

For a fully funded three-account period, US$13.50 divided by 12/13/14 issues is US$1.125/1.03846/0.96429 per issue **before overhead**. These are planning shares, not evidence that every issue costs that amount. Allocate remaining funds using actual upcoming issues, selected source envelope and outstanding commitments; a fifth batch creates no new funds.

Each account may have a different renewal date. New billing dates or keys must not reset old charges, holds, origin account or pending remote jobs. Free-credit rollover is not assumed.

Research-week limits are separate from provider periods. A duplicate weekly start resumes its persisted allowance; a genuinely new due week can receive one new finite work envelope within existing funded headroom. That creates neither credits nor another trial grant. Carried tasks keep original acquisition/job/attempt/account references, and a new week never authorises replacing an uncertain launch. Missed weeks do not accumulate automatic catch-up allowances; implementation is specified in plan21.4.

## 5. Multi-account financial implementation and remaining activation

The implemented seam is `accounts.load_account_registry/context_for_account/context_for_origin/choose_account`. The existing `MetaTrial` controller and CLI automatically use the pool only when a valid private registry is present. Otherwise legacy calls and all original financial records retain their existing behaviour. The public non-secret [registry example](../../config/benchmarks/apify_accounts.example.json) contains one existing-profile reference and two disabled, unsupplied profiles. It contains no key bytes or balance claims and is not an active configuration.

For each new acquisition, the router checks the actual saved account identity, credential generation, period, dated owner balance, existing funded source allocation, unsettled commitments and finite request cap. It chooses in declared stable priority order and skips an unavailable profile without inventing funds. Names and keys cannot create a second allowance for the same real provider identity. The explicit `bind-account --account-id <private-profile-id> --live` command performs bounded access/identity reads before adding genuine funds once; it does not launch an Actor. `account-status` reads no key and reports known actual charges separately from holds. Its total includes all historical journal periods, including profiles no longer listed.

The account origin and original private binding/profile snapshot are frozen before provider activity. Exact replay keeps the same account/period/generation/configuration and cannot reselect a richer account or relaunch. A same-period replacement secret uses an authenticated same-account binding and an explicit `authorise-recovery --account-id <replacement-profile-id> --original-generation <saved-generation>` record for old reads. At genuine monthly renewal, the explicit binding command verifies that same provider account, confirms that the previous saved period has ended, preserves every old run context before replacing the private slot and records a separate dated new-period balance. An actually authenticated new-period key may then supply old-run reads through a private recovery-only identity receipt; the saved run generation and Actor bill never change. Retained dated context permits safe old-run status reads, and new potentially billed storage reads use the separately reserved current funds described below. The old one-account expired-period guard remains unchanged.

In pool mode, the lock order is exact-attempt guard → short money transaction for reservation and durable submission intent → release money lock for provider work → short receipt/charge/capture commits → release exact-attempt guard. Old single-account callers retain their existing locked contract. The existing CLI/batch callers use the appropriate path; new-pool calls reject an externally held money lock rather than accidentally carrying it across network work. A synthetic complete preflight, launch, terminal billing, capture and resume proves all network reads happen without the money lock. Lost replies retain the original uncertain submission and hold; healthy independent account/source work can advance.

`research_costs.collection_costs` charges each supplied physical acquisition once, retains failed collections, and separates known actor/read fees from unknown holds. `yield_forecast` uses the supplied baseline expense/candidate count and a declared useful-yield scenario; it cannot establish that the supplied candidates finished screening. Five-/three-percent scenarios require more ideas and more money rather than multiplying only successful report entries. Its output remains collection-only when AI/direct-source/hosting costs are unknown. Per-issue ceiling of required ideas is slightly more conservative than monthly pooled rounding in the illustrative table above.

Activation requires genuinely supplied additional credentials and their account/period evidence; these are not yet all present. No active three-account registry, new paid provider run, new funds, purchase or actual usage settlement is created by this implementation. The historical US$0.50040006 and US$0.88 read holds remain original dated records. Focused synthetic fixtures cover identity/alias duplication, disabled missing keys, original-account recovery, replacement credentials, period changes, per-account uncertainty, short launch transactions, lost responses, exact renewed-read costs and yield math. The account-pool suite currently contains 45 such passing cases; this is local behavioural proof, not provider activation or an accepted live monthly bill.

Use a private three-profile registry with stable account ID, private key reference, generation, actual period, balance observation/time/precision and active scope. Keep all historical namespaces and attempts. A same-account key replacement is not a new allowance.

A deterministic router first recovers an existing task with its **original** account. For new work, evaluate each approved account's actual funded headroom, current period, existing commitments and support for the selected Actor controls. Choose an account capable of covering the finite request within its approximate target, preferring the account already suitable for that work and then stable registry order. Near-target uncertainty can switch **new work** to another funded account; existing runs/results never move accounts. A verified replacement key for that same original account can recover its old run through an explicit credential-recovery record; account/period/generation provenance and funds remain unchanged.

Distinguish account-scoped unknown submission/collection recovery from read uncertainty. An uncertain paid launch is reconciled before another launch for that logical request. Unknown reads retain allowances but must not stop unrelated saved analysis or every other funded account. Aggregate project planning still includes all accounts' liabilities.

**Implemented recovery reads after renewal:** the optional pool's `MetaTrial.before_request` keeps original attempt, account-period, generation and run provenance. `accounts.current_read_funding_context` resolves only the genuinely bound current period of that same provider account; it never borrows another pool account. `Journal.reserve_renewed_reads` moves at most US$0.02 of that current period's already-approved source allocation into one named read envelope before any potentially billed storage GET. This records the original attempt, actual funding account-period/generation, dated period end and private identity/funding proof. A repeated invocation reuses the envelope, not another allowance. The journal stores a unique operation before each request and later stores received byte counts. Current funding adds neither a new Actor launch nor another benchmark grant.

Both the original acquisition and its renewal envelope retain bounded read activity: at most 40 storage calls and 50 MiB across the original acquisition's lifetime, with individual reads at most 5 MiB. A renewal does not reset those lifetime limits. A lost response keeps its full possible byte exposure and unresolved US$0.02 hold. Saved raw responses can be replayed without a second storage GET. Local admission/commit failures keep the original attempt and bounded reservation for recovery; they are not permission to launch the Actor again. Missing current account facts, an exhausted allocation, or an unproved replacement identity pauses only that read while independent saved analysis and other funded work continue.

Settlement is an offline operation. Save an exact `operator_confirmed_read_usage` proof under the original attempt's `funded_reads/<read-id>/read_cost.json`, naming the funding period/generation, complete original operation-ID set, dated amount and reason, then run `settle-renewed-read --attempt-id <original-attempt> --read-id <funded-read-id>`. The command makes no provider/model call and cannot infer a zero fee from a missing record. Duplicate identical proof adds no second charge; a later higher attributed fee is appended, including an overrun, and blocks further spending against that funding account rather than erasing the bill. Only unused **known** commitment is returned to its same source allocation. Original Actor fees, original read fees, old holds and historical journal bytes remain unchanged.

Saved account status and the collection-cost helper show the new read fee/hold separately. The owner-only cost/capacity summary is now connected in code to one final programme checkpoint and the default read-only status command, as described in section 7. Automatic per-issue shared-cost attribution remains unallocated because no actual allocation rule has been supplied. A fee already reflected in a dated provider balance is not subtracted again as an unresolved hold. A successful capture or recorded fee is not a claim that the report's data quality is accepted. Real additional-account activation and real exact read-usage attribution remain unproven; this implementation is not a purchase, automatic balance top-up or new billing service.

The implemented pool refactor changes the controller and financial lock together; a registry alone would not work. It uses an exact-attempt guard, short locked reservation/submission intent, network launch without the financial lock and short locked result/charge commits, with saved-receipt recovery before any retry. The preserved single-account contract still requires its own held-lock path; never simply move that legacy `run()` outside its required lock.

Migration copies no money and resets no history: register the existing account/period from current evidence, preserve the original US$0.75 trial and US$3.75 future commitment, then record any newly verified approved-account funds and planned aggregate allocation explicitly. No multiplication of the original trial allowance by three.

## 7. Ongoing measurement and decision rule

`programme_owner_summary` connects `programme_summary.programme_cost_capacity_summary` and `programme_cost_snapshot.build_owner_cost_snapshot` to one final parent checkpoint, not every stage or child. Pending control retains the owner-only aggregate; the default read-only `run_programme.py` shows current counts without executing research or changing that checkpoint. One verified research state and one short saved financial pair are reused. Report counts use the actual allocator and frozen-inventory/publication/reservation filter. Generated packets and retained original versions are counted separately from allocation proposals. Exact known project spending divided by genuinely generated logical issues is an explicitly changing shared average, not an exclusive report bill or future unit price. Current read-only output is proved; an already-imported live process does not automatically load later reviewed changes.

The summary separates admitted family/phrase/source/purpose choices, actual acquisition attempts, known fees, unsettled holds, saved account headroom, eligible reserved/unreserved New stock, current allocations and shortfalls. Holds are not bills; saved headroom is not a current provider balance. Original156 reviews, exclusions, newly admitted concepts and report readiness stay separate; seed examples add no capacity. The selected public156-candidate historical collection baseline and current calendar automatically produce named5%/3% conditional forecasts: October's14 issues are US$8.98153954/US$14.99917103 collection-only. This is not current direct-source yield or a complete bill.
