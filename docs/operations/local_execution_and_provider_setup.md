This guide owns owner actions and access/recovery procedures. [Progress](../project/pj-tracker.md) owns dated status and open choices; the [product contract](../product/india_dropshipping_product_opportunity_radar_product_brief.md) owns selection/report rules; [Plan R19](../project/plan-2026-10-17-r19-product-flow-engine.md) section 3.8 owns AI cost and the credit budget.

## 4. Joined programme and weekly workflow

The joined driver, finite free-discovery callback and separate follow-on review scopes are implemented. `NeuraFlow-Dropshipper-Research` is installed and enabled in Windows; the repeat-install comparison preserved the matching task, and a scheduled check returned0 with no second research writer observed. Whole-pool unattended completion remains under acceptance. It preserves the current full-source identity, continues independent work after failures and keeps report size separate from research completion. `scripts/run_programme.py` is read-only by default; `--prepare` makes no research calls. `--pause` prevents the next bounded stage/model launch and `--resume` keeps the same saved work/funding. Neither kills an already dispatched request. Keep this one task and the kernel guard; do not create independent competing research writers. After a genuine saved fixed point, weekly discovery can proceed without cloning the old product pool; due old/new work rotates by its last serviced time.

**Progress watch.** Each research run saves its activity in `data/operations/research-runs/` (one log per run plus `current.json`); every record names the exact code that ran (`code_version`, a fingerprint of every Python file of the program). Long local checks save a small "still working" note at most every 30 seconds. The desktop worker watches its own research run: after 45 minutes with nothing recorded it stops that run the way Stop does (Ctrl+C first, harder only after 5 and then 1 more minute), leaves the research switch on and saves a `watchdog_restart` receipt, so the next scheduled run starts research again. The window warns after 30 minutes without activity or without a completed result, when the same problem ends 3 runs in a row and when no scheduled run has started for over 20 minutes while research is on. Thresholds: `config/research/progress_watch.json`. Owner view: [desktop guide](windows_desktop_launcher.md#progress-watch-warnings-and-the-automatic-restart-of-a-stuck-run). Run logs untouched for 90 days are removed once a day after their totals are kept for the owner meter, and unused research lookup pages are removed after 24 hours.

The complete operator experience below still needs whole-pool, fresh-discovery, recurring financial/history and private-release acceptance; a joined function is not completed operation.

Manual and scheduled AI work use the same validated installed program selected in `config/ai/codex_luna.json`, and the connection checker uses that same selector. The explicit path does not change the chosen account/model or create a new saved request. A missing or incompatible program defers only new AI launches; saved answers and other ready work continue. Preserve failed execution receipts and prepare only an inspected, reconciled request for a deliberate retry. See [AI connection and recovery](providers/codex_luna_connection.md#one-executable-for-manual-and-automatic-work).

1. A small scheduled start normally runs on Monday in the environment that actually supports the browser/model. It checks saved jobs, source capability, period/funds, disk and settings. A duplicate start resumes the same research-week allowance; a genuinely new due week creates one finite envelope and carries useful unfinished references. It does not reset old executions or add provider funds; explicit service stop remains respected.
2. Reconcile server release history and queued reservations. Show upcoming Tuesday/Thursday/Saturday 09:00 India dates and actual monthly/provider-period headroom.
3. Recover exact pending work; interpret saved material; finish useful missing source checks; choose fresh focused research using catalogue feedback rather than repeated broad-category searches.
4. Persist outcome after each action/chunk. A failed route records its exact reason/next trigger and leaves independent work running. Unknown reads retain allowances; another funded approved account may take new work under the planned router.
5. Fill ten eligible allocations for each due issue before extras. Use all published history and queued holds: at least 80% New, at most 20% genuine useful updates. If only 25 qualify, prepare earlier complete issues and show the remaining shortfall—no automatic five-product publication.
6. Perform or reuse properly scoped real supplier effort for every selected product. Prefer stated no mandatory subscription and useful fulfilment; unknown/bulk limits remain visible. If actual attempts give no usable results, even because routes/pages fail, keep an otherwise eligible product and show “Supplier search did not produce any usable results.” Prepared links alone are not actual effort.
7. Freeze issue facts and prepare usable PDFs/workbook with real photographs when captured, source figures, short reasons, supplier terms and clickable links from those same facts. Keep the existing presentation for this nonvisual programme. Check actual supporting-source expiry at the intended release time, not only its date; address only affected stale evidence.
8. Filling an issue does not stop the remaining finite run. Continue useful saved interpretation/evidence/supplier work for later reports within the original allowance. Do not start unlimited new work.
9. Show the owner the actual files and a concise internal summary: queries/areas, real attempts, repeats/New/carryover, eligibility/blockers, supplier coverage, costs/holds, completed issues and precise unfinished work.
10. Correct source/template logic when an error is found, run its regression and generate a new affected revision. Never manually patch PDF facts or overwrite old frozen packages.
11. Obtain exact owner approval for complete revisions. Stage private objects, read them back and conditionally commit the approved release index. Client email and access are completed only when supplied.
12. Confirm approved complete packages and server release dates before switching off the local computer. The server then releases them independently; unfinished local work still requires the computer to run.
13. Preserve source/publication/accounting history and back up essential records/files to the owner-selected project-local `data/backups`. Verify an isolated restore; this same-drive copy is not physical-drive-loss protection. After each new verified daily copy, copies beyond the newest 14 days plus one per week for 8 weeks are removed with the stored files only they used; below 10 GiB free on that drive no new copy starts (`LOCAL_BACKUP_DISK_SPACE_LOW`) and research continues. Numbers: `config/operations/durability.json`.

The first two **distinct published issues**, not two revisions/language files, require both languages. Prepare the third's research/facts and independently bound workbook while language is pending; finish its chosen PDF after the client decides. Do not hold the first complete approved issue waiting for a second, or hold both waiting for the third's language.

## 5. Private-file delivery check

Existing checker: `scripts/check_portal_private_delivery.py`. Default checks use two fixed hash-pinned illustrative artifacts. An explicitly authorised `--live` check stages only internal private keys through the existing `PortalStorage`, verifies actual bytes and unchanged release-index body/ETag, and never approves or publishes a report. A complete ten-product report is not needed for this object-only transport test. It is not proof of live report design.

Historical revision6 upload/download proof does not establish a current owner session. If the current session expires, use the existing official finite `cloudflared access login` helper once when the owner is available; use a fresh one-time link, not repeated unattended attempts. The token is supplied privately in memory, not pasted into chat/commands/logs or extracted from browser cookies. Dashboard/management-plugin sessions are not replacements.

Retain the separate private-file receipt. Successful login is not successful file upload; the actual byte readback proves the named internal objects, not client publication or all future reports. A lost write response is reconciled by remote bytes/hash/index, not a blind repeated write.

Unattended staging uses the specifically scoped Access application under `/_automation/drafts` and ignored `config/local/draft_automation.json`, not the owner's session. The Worker retains the service Client ID as a separate secret binding; the service secret stays only in the private local file. Public machine audience/team settings belong in the normal Worker configuration so later deployments preserve the connection. Before storage, verify the trusted machine audience and service identity, using a cryptographically verified fixed-team assertion only when the provider identity lookup is missing/unavailable. The machine can read the release index and read/save the four or five validated immutable packet files. It cannot approve, publish, change that index or use owner pages. The owner-only download-link check remains separate. Missing service access postpones only staging, not research or local report generation.

The historical machine-connection check verified all five original revision6 files, one same-byte immutable PDF save and an unchanged empty release index. The current marked-source/photo validator is deployed; all10 existing bindings/settings stayed unchanged and post-deployment reads verified all five file hashes plus the three owner downloads. Its [sanitized receipt](../../archive/2026-10-13-before-fresh-start/data/operations/portal-deployments/draft-automation-20261008.json) contains hashes/status only, not credentials. The verified signed audience accepts an exact single string or a bounded array containing that exact value, as allowed by RFC7519; both still require the correct issuer, service identity, times and signature. This is existing-packet connection acceptance, not a new expanded report or client release.

If this computer reaches an old Vercel route instead of the configured Worker, compare current local and public domain lookups before changing settings. A temporary command-only verified connection is a diagnostic check, not a permanent browser-DNS requirement or production fallback. Do not disable HTTPS verification, edit unrelated domain records or require a permanent browser setting change.

## 6. Problems and the next useful action

This table is the operating response contract. Decision/binding checks, supplier effort, saved-job recovery, partial internal files, account routing and scheduling are connected locally. Draft-only machine storage and owner downloads have actual separate proof. Complete whole-pool operation, recurring recovery and approved client release remain under acceptance; the table does not claim that every fallback has been proved in unattended service.

| Situation | Operator/program response |
|---|---|
| Fewer than ten eligible products for one issue | Preserve draft, exact counts and reasons; discuss that shortfall. Continue independent issues/useful work; no weak padding or silent smaller issue. |
| Source blocked or chart sparse | Record actual route/product attempt, stage/status/time; unavailable or insufficient is not zero demand. Try only a finite permitted alternative when useful. |
| Shared outage across routes | Group the common observed transport/access problem; do not retry every product/account. Use valid saved work or another ready lane; schedule one bounded due recovery probe. |
| Repeated products/queries | Reuse exact saved work, use alias/function history, update feedback/cooldown and select a useful new area. No default ever-deeper paging. |
| Possibly running or uncertain paid submission | Recover original account/run/receipt before any new POST. Other saved analysis continues. |
| Unknown read fees | Retain existing holds and show uncertainty; do not require every historical read settled before all work can proceed. |
| Original key or provider period expires | Keep the original account/run and verify replacement credentials for that account. Any new billed read needs explicit current-period funding while original fees/holds/lifetime limits remain; do not move the job or create credits. |
| Supplier/fee/dispatch/photo unknown | Show that exact limitation and preserve useful product work. No invented supplier capability or photo; no new mandatory certification. |
| Every attempted supplier route fails or gives nothing usable | Preserve exact internal receipts/next trigger. After real bounded effort, include an otherwise eligible product with “Supplier search did not produce any usable results.” Do not claim supply is absent or call failed searches successful. |
| Model limit or interrupted process | Preserve accepted siblings/results; reconcile owned execution before the finite allowed retry. No paid fallback or unchanged repeated calls. |
| Facts saved but writing/rendering partly fails | Preserve frozen core facts, internal workbook and valid separate language stages. A local failed chunk, correction or problem-record save retains the completed language and records a fixed safe reason, including when a problem record could not save. Resume missing work from exact saved answers; no second model call or rerender of valid unchanged English is needed. Required bilingual issue stays incomplete until both editions pass. |
| Owner unavailable / client email missing | Pause only transport/approval/client activation; continue dependency-ready internal work. |
| Ongoing language not chosen | Pause only the third language package; first two complete bilingual issues can proceed independently. |
| Render/upload/index conflict | Preserve prior valid release/incomplete artifacts. Check whether the exact approved activation already committed before rejecting its original saved ETag; otherwise reconcile genuine conflict, never silently overwrite or refresh approval. |
| Late/cancelled/replaced issue | Recheck affected novelty, language ordinal, source expiry and remote reservations. Published availability stays in history. |
| Material supply/budget conflict | Provide measured cost/yield/queue numbers and options. No automatic purchases or silently changed five-of-ten inclusion/four-level source priority/ten-product floor. |
| A few cents of variation | Absorb within approved actual funded limits and finite scope; do not interrupt for penny-level approvals. |
| Canonical record cannot be saved/trusted | Do not launch dependent charged/model work without durable intent. Retain outputs/last committed position; hosted reports remain intact. If the authoritative event saved and only the optional index failed, retain the successful application and rebuild the index; do not repeat external work. |
| All remaining work waits, limits ended or computer was off | Save queue/consumption/trigger. Resume same-period remaining work or carry useful backlog into one new due-period envelope. No unchanged loop, accumulated missed allowances, cancellation bypass or promise of local work while off. |
| Research stuck with nothing recorded | The window warns at 30 minutes; at 45 minutes the worker stops only that run and the next scheduled run restarts research (switch stays on, `watchdog_restart` receipt). Nothing for the owner to do unless it repeats. |
| The same problem ends 3 runs in a row, or no scheduled run for over 20 minutes | The window shows "Needs attention" with the problem in plain words and one notification. Research keeps retrying; a repeated problem needs a code or setup fix. A late schedule: click Stop, then Start, and check the Windows task. |
| Research site sign-in needed or expired | Only that site's routes wait (`OWNER_SIGN_IN_REQUIRED`); the window and one notification say which site. Owner signs in again (section 8.1). |
| Quick-commerce credits or Apify month used up | That money route waits; free work continues. Owner buys the ₹500 quick-commerce pack when asked (section 8.3); Apify resumes with the next free month (section 8.2). |

A problem record includes expected/actual, affected action/product/issue, confirmed versus suspected cause, safe evidence, possible remote charge/running state and next trigger. Group repeated route failures; do not ask the same unanswered setup question repeatedly.

Not every lane's recovery is automated. P2 keeps valid products moving when a sibling fails, reuses exact saved review answers, ties brand corrections and supplier effort to the right product, and retains a successful main-record save even when its optional quick-view index fails. Different ready tasks can proceed during a wait; running blindly again is not recovery. If the main saved history cannot be trusted, dependent changes wait without deleting old work or affecting already-hosted reports.

## 8. Signed-in research sites, allowances and the R10 cutover

Built on branch `r10` (Plan R10, waves 1–4) and loaded at the W13 cutover; until then the running research uses the older code.

### 8.1 Signing in to the research sites (owner, once and whenever a sign-in expires)

Google Trends, IndiaMART and Dropdash are read in the program's own Chrome profile while signed in with the separate research Gmail. That profile lives in the owner's Windows account (`%LOCALAPPDATA%\NeuraFlowDropshipper\research-browser-profile`), never in the everyday Chrome profile, Git or the daily backups. The program never reads, stores or prints passwords or cookies.

1. Open the **NeuraFlow Dropshipper** window and click **Sign in to research sites**. (Command alternative: `.venv/bin/python scripts/research_sign_in.py open`.)
2. A plain Chrome window opens with six tabs: Google, Google Trends, IndiaMART, DeoDap, BaapStore and Dropdash. Sign in on each; DeoDap and BaapStore need no sign-in because their whole public catalogues are read without it (the owner checked on 15 October; their paid plans are never bought). Dropdash's form asks for the account's **10-digit mobile number** and password; an e-mail address is refused ("Please enter valid 10 digit mobile number"). IndiaMART's tab shows its own mobile-number sign-in: enter the mobile number and the one-time code IndiaMART texts to it (as of 16 October the research profile had never been signed in to IndiaMART).
3. Close the Chrome window. While it is open, signed-in reads wait (`OWNER_SIGN_IN_WINDOW_OPEN`) and never close it.
4. The sign-in line in the window clears after the next reads see the sites signed in. `.venv/bin/python scripts/research_sign_in.py status` reports each site as signed in / sign-in needed / expired / not checked from what the latest reads saw; it visits no site.

If a read meets a site's sign-in wall, that site's sign-in is recorded as expired: its routes wait with `OWNER_SIGN_IN_REQUIRED` (a question that met the wall waits calmly for the sign-in and keeps its try limit), the window shows "Sign-in expired: …" and Windows shows one notification. Everything else keeps running. Signed-in reads use a real window that starts minimised without taking focus; Chrome's own focus emulation keeps the page drawing while it stays minimised; while Windows is locked or signed out they wait (`OWNER_DESKTOP_UNAVAILABLE`). If the button says a research read is using the browser, try again in a minute.

On the signed-in sites the program only reads: it never pays, accepts a plan or membership prompt, or clicks contact, "View number", "Get best price" or "Send enquiry". A plan or membership page on Dropdash makes it wait (`DROPSHIP_PLAN_REQUIRED`) and shows a line in the window. (Dropship India was dropped by the owner on 15 October 2026 because it showed nothing useful, signed in or not; the program no longer opens it.)

After each new sign-in, Google Trends must pass its proof gate: three complete signed-in reads including at least one verified chart export. The window's Trends line shows the count; if Google still refuses, the route stays blocked with the exact reason and research continues without Trends.

### 8.2 Apify: account list and automatic monthly renewal

The deeper Meta read (`meta-ads-depth`) uses only the free monthly Apify allowance of the one funded account. Each month US$4.45 is earmarked for it and US$0.55 is kept back (the US$0.50 buffer plus the ledger's five-cent tolerance; `config/research/apify_allocation.json`). At the buffer the route waits for the next month.

The account list must be switched on once at cutover so that each new Apify month is recorded automatically: `.venv/bin/python scripts/enable_apify_account_list.py` (also done by `scripts/r10_cutover.py apply`). It writes ignored `config/local/apify_accounts.json` naming the existing private files of the one funded account; it reads no key, calls no provider and adds no unfunded account. With it on, the program reads Apify's free monthly limits endpoint, records a new month for the same account and key, and earmarks it. If the saved key cannot read the monthly usage (`APIFY_LIMITS_READ_DENIED`) or the account shows a paid plan (`APIFY_PAID_PLAN_REFUSED`), deeper reads pause and the spend watch shows a plain notice after six hours. No paid Apify plan is ever used.

### 8.3 Quick-commerce credits and packs

Blinkit, Zepto and Instamart are checked only through the provider's paid API (one credit per successful search), only for types that pass the checklist with Low or Medium crowding: Mumbai first on all three apps, Delhi NCR and Bengaluru only after a relevant Mumbai result, and the same city not again within 30 days (types in an upcoming issue are refreshed after seven days). Estimate: 3–9 credits per type and about 300–900 credits a month at present research speed.

The free balance check runs before each batch. A zero or unknown balance makes the route wait (`QUICKCOMMERCE_CREDITS_EXHAUSTED`) while all other work continues. When the window's quick-commerce line says the credits are low or used up, the owner buys the **₹500 pack (2,500 credits, valid 30 days)** at quickcommerceapi.com (Pricing → Starter). The program finds the new pack in the provider's pack list with its expiry, records its price from the published table, clears the wait and resumes. Pack expiry is flagged three days ahead. The program never buys anything.

### 8.4 The R10 cutover (lead, W13)

1. Stop research cleanly (desktop **Stop**, or `scripts/desktop_research_control.py stop`).
2. Copy the working-records folder to a dated backup folder; older code cannot read records written by the new code.
3. `.venv/bin/python scripts/r10_cutover.py check` (read only): reports stock frozen under the old Meta rule, Trends waits set against the old hidden browser, open questions of retired routes and any missing settings file.
4. `.venv/bin/python scripts/r10_cutover.py apply`: switches on the Apify account list, releases the old Trends waits and expires, with a recorded reason, report stock frozen under the old Meta rule so it is judged again. Repeating it changes nothing new. No provider, website or model is called.
5. Load the new code and start research; then run the W13 live checks listed in the implementation record.

### 8.5 Spend watch and the meter

Every allowance has one saved record: Apify per account month, quick-commerce credits (used against credits held in active packs), each AI usage window Codex reports, money this month in rupees (₹750 target, review above ₹1,000, US$1 = ₹100 planning rate) and the Cloudflare free plan (not polled). Each is flagged once at 50%, 75%, 90% and 100% per period; at 100% a money route (Apify, quick-commerce credits) waits while free work continues. AI is never paused for allowance use; it waits only to protect money (`AI_PLAN_LIMIT_CREDITS_PROTECTED` when a plan limit is reached, `AI_PAID_CREDITS_USED` if paid Codex credits fall during a research call), resuming after the window resets.

Where to see it: one line per item in the desktop window plus one Windows notification per new flag; `scripts/run_programme.py --meter` sections `allowances`, `trends_check`, `crowding_check` and `platforms` (read from saved records, no provider call); the dated alert log under `data/research/captured/spend_watch/alerts/` in the working-records folder, included in daily backups.
