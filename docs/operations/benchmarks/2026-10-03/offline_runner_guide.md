## Saved fit projection and named review

Codex first projects applicable **saved** judgments, without collecting or asking the model to rescore everything:

```bash
.venv/bin/python scripts/benchmark_providers.py research-project-fit --item-limit 10
.venv/bin/python scripts/benchmark_providers.py research-project-fit --concept-id '<exact-current-concept-id>'
```

This offline action verifies current product/evidence/brand bindings, appends a ten-row current assessment, retains supported unchanged rows and preserves original jobs, captures, financial history and frozen packets. Unsupported judgments become unknown, not automatic failures. IDs 7/13 are left unknown while an exact saved review base is prepared for their changed meaning. A named product without an assessment gets a saved full-ten question instead of fabricated rows. The bulk default is 50 healthy projections, adjustable 1–50; stale/excluded/bad-binding products record their own outcome and do not consume the healthy allowance or prevent usable siblings from advancing. A replay returns the same application/question without another event or network/model call.

Inspect the returned `review_id` values and choose only useful pending questions. There is no review-all command and no need to recollect listings to answer them:

```bash
.venv/bin/python scripts/benchmark_providers.py research-review-fit --review-id '<exact-saved-review-id>' --live-model --item-limit 5
.venv/bin/python scripts/benchmark_providers.py research-review-fit --review-id '<first-saved-review-id>' --review-id '<second-saved-review-id>' --live-model --item-limit 5
.venv/bin/python scripts/benchmark_providers.py research-summary
.venv/bin/python scripts/benchmark_providers.py research-ready
```

`research-review-fit` requires at least one unique `--review-id` and `--live-model`. The named-ID count cannot exceed `--item-limit` (default 10; range 1–50). Compatible questions are grouped into batches of at most 5. The frozen base contains exact description/evidence/brand hashes, parent assessment, retained rows, requested criterion IDs and reason. Only supplied public research and earlier public judgments go to the already-approved signed-in model; no passwords, private account/client records, supplier contact, paid collector or publication is part of this action. Do not add `--live`, `--reason` or `--concept-id` to this command; those are not accepted review arguments.

Validated responses fill only their requested rows. Stale bases cannot overwrite newer judgments. A saved original job/result/completion is reused even when batch shape changes; an applied review returns its application receipt. A possibly running, failed or unavailable execution stays precisely pending/reconciliation-required instead of silently starting a different job. Valid siblings continue. Refreshing summary/readiness does not itself perform the pending model reviews or prove the product ready.

A failed local sign-in check does not automatically mean the owner is signed out. Only recognised explicit sign-in/API-key-authentication responses produce that diagnosis. Permission/configuration/network failures and unknown errors retain their own or neutral local-execution cause. Before model launch, the runner saves a small `runner_preflight.json` tied to the exact job/attempt/request/intent; it records the failure stage/code/exit or exception class and unknown usage, without raw output, account data or credentials. A deliberate retry of a neutral failure is allowed only when that exact valid receipt proves no model started and no execution/completion/result exists. An uncertain live execution or a historical generic failure without this proof is not silently retried. The chosen signed-in model and read-only, tools-disabled analysis remain unchanged; no automatic API or credential fallback is introduced.

New `research-run --live-model` and batch interpretation use schema version 3's current policy. In the Python API, `run_flow` without an explicit policy remains the historical boundary; production callers pass the loaded policy. Tests or tools deliberately replaying old work must use its saved contract rather than temporarily change the production configuration. Only the benchmark's actual saved-data/model/sample results establish acceptance.

## Brand and identity corrections

Ordinary A interpretation supplies the initial moderate brand judgment. A manufacturer name alone is not an established-brand exclusion. The existing `research-brand-review` command is the older **exclusion-only** inspected-source route; it does not implement restoration.

A named restoration/current-verdict correction uses the existing Python API, not an invented CLI flag:

- `brand_reviews.prepare_brand_review(state, target_kind, target_id, *, verdict, reason, evidence_ids, reviewer, reviewed_at)` prepares the exact source-bound request.
- `brand_reviews.apply_brand_review(memory, request)` appends that prepared request and returns its application outcome.

The caller supplies `target_kind="concept"` or `"child"`, the exact current ID, verdict `generic_or_small`, `established` or `unclear`, a reviewed reason, actual saved observation IDs, reviewer ID and timezone-aware date. Preparation freezes the description, sources, relevant associations and superseded review. Apply refuses changed dependencies or conflicting verdict history; exact replay reuses the original application. This is an explicit source-reviewed correction, not a website fetch, manufacturer-name blacklist or automatic new model decision.

A brand-only excluded child may return to ordinary identity processing. A valid corrected child verdict carries into a **newly created** concept without overwriting the original A answer; matching that child to an existing concept does not replace that concept's own verdict. An unchanged functional supplier scope can retain earlier real effort despite a brand/audience judgment change. A real function/mechanism/features change needs separately applicable sourcing evidence. These corrections do not waive category, identity or held/published-history checks. Frozen/published packets remain unchanged.

For a reviewed unallocated identity merge, use `identity_corrections.apply_unallocated_identity_merge(memory, request)`, not an automatic title merge. Supply 2–20 current IDs, one existing survivor, complete `concept_hashes`/`association_hashes`, actual `evidence_ids` for each member, `author`, `reason`, timezone-aware `reviewed_at`, and optional `survivor_description`. Decorative bear/bird/elephant bookends can share a functional recommendation; a genuine folding/adjustable mechanism may differ. Code verifies current A/capture bindings and contradictions and refuses published or active-held members across clients, including incoming redirects. One append preserves old identities and original B provenance. Exact replay adds no event; changed inputs are refused. Refresh affected fit/relevance and explicitly recheck supplier/chart scope: no E/F/Trends result is copied. Splits and released-history migration remain later work.

## Supplier receipts, effort and interpretation
